# L3 混合编译 · 架构说明

## 一句话

Hybrid-QASM 进去，量子指令序列和 RISC-V 汇编出来。判定是完全确定性的，所以这一级的
全部功夫都花在**「我怎么证明它对」**上，而不是花在设计上。

```
hybrid 源码
  └─ quantum.split()        先按花括号配对把 classical 块整块抠出来，再切分号
       ├─ 量子部分 → 归一化后的门/测量语句列表（按程序顺序）
       └─ classical 块 → grammar.parse_classical()  按题面那行 EBNF 解析
                            └─ codegen.compile_block()  只用 7 条指令
```

`interpreter.py` 单独写了一份参考语义，定义「这段汇编应该干什么」。测试拿随机生成的
程序，穷举注入所有测量值组合，把汇编在官方模拟器里的寄存器终态和参考解释器逐个比对
——就是题面描述的判分流程本身。

## 寄存器映射（唯一一个可能让整级归零的假设）

```
r1..r9   ->  x1..x9          可写的经典寄存器
c[k]     ->  x(10 + k)       测量结果，评测系统注入
```

题面原话是「测量位 `c[k]` 依次映射到 `x10, x11, ...`」。这句有两种读法：按**经典位下标** k
映射，还是按**测量语句出现顺序**映射。两种读法在公开样例上结果一样（只有一个测量），
分歧只在乱序测量时才出现，比如 `measure q[1] -> c[1];` 写在 `measure q[0] -> c[0];` 前面。

**本实现按下标**——`c[k] → x(10+k)`，与语句顺序无关。理由是「`c[k]` 依次映射」这个写法
主语是 `c[k]`，而且公开 evaluator 里 `set_register("x10", measured)` 对应的正是 `c[0]`。
这条要是猜错了，乱序测量的用例会全错。

## 为什么不能复用 L1 的解析器

L1 的 parser 明确拒绝「对已测量的比特再施加门」，那是它的一条安全检查。而 L3 的公开
样例正好就是这个：`measure q[0] -> c[0];` 之后又来 `cx q[0], q[1];`。中途测量正是 L3 的
题眼，所以 L3 自己写了一个语句级的抽取器，只做归一化、不做那条检查。

另外 `classical { ... }` 块里有分号，必须**先按花括号配对整块抠出来**，再对剩下的部分切
分号，否则块里的 `r1 = 100;` 会被当成量子语句。

## 代码生成

模拟器只认 `li add sub addi beq bne j` 七条指令，没有 `mv`、没有 `slt`、没有伪指令、
**没有任何访存指令**。于是：

- `mv rd, rs` 写成 `addi rd, rs, 0`
- 比较不产生标志位，一律编译成分支。`if` 里的顶层比较直接编译成一条反向分支
  （`a == b` → `bne …, else`），不先物化成 0/1
- 表达式里出现的比较（`r1 = r2 == r3`）才物化成 0/1，用两条 `li` 加一次跳转

一条容易写错的地方：**整个右值先算进临时寄存器，最后才写回 x1..x9**。如果直接把左操作数
算进目标寄存器，`r1 = r2 + r1` 会在算到一半时把 `r1` 冲掉。

临时寄存器从 x31 往下取，测量窗口从 x10 往上排，两头相向而行，碰到就报错而不是继续。

## 三个硬上限（都是 ISA 本身的，不是实现偷懒）

| 限制 | 数值 | 原因 |
|---|---:|---|
| 表达式嵌套深度 | 20（2 个测量位时） | 没有访存指令，临时值无处 spill，寄存器堆用完就是用完 |
| 测量位数量 | 20 | `c[20] → x30`，再多就没有临时寄存器了 |
| 程序长度 | 约 250 条语句 | 模拟器 `max_steps = 1000`，一条简单赋值约 4 条指令 |

超出前两条时抛 `CodegenError`，不会静默算错。第三条是模拟器的死循环保护，我们生成的是
直线代码加分支，执行条数不会超过发射条数。

## 语法上放宽的一处

题面那行文法没说末尾分号能不能省。本实现**允许在 `}` 或块尾省略最后一个分号**——语法在这
两个位置本来就不歧义，而为一个分隔符丢掉一整个生成用例是更差的交易。块中间漏分号仍然报错。

`else if` 链、括号、一元负号、块内注释、以及完全不带空格的紧凑写法都接受。

## 验证

```bash
python3 -m unittest tests.test_l3_hybrid -v
```

33 个测试，纯标准库。核心的那几个是 `ExhaustiveEquivalenceTests`：按题面文法随机生成
程序，编译，在**官方 `riscv_emulator.py`** 里穷举注入每一种测量值组合，把 x1..x9 的终态和
参考解释器逐个比对。

测试里跑 210 个随机程序（够快，能进 CI）。开发时另外扫过一轮更大的：

```
4800 个随机程序 × 全部测量值组合 → 0 处不一致
```

生成器的构造覆盖（200 个程序统计）：`if` 955 次、`else` 398 次、`else if` 115 次、
嵌套 `if` 170 次、表达式里的比较 256 次、一元负号 1131 次、多个 classical 块 68 次。

公开自测（L1+L2+L3 全开）：

```bash
cd starter_kit && python3 evaluator.py --target spinq,originq,braket
# {"passed": 8, "failed": 0, "total": 8}
```

## 当前验证状态

| 项目 | 验证方式 | 结果 |
|---|---|---|
| 公开样例两个分支 | 官方模拟器实跑 | 通过 |
| 随机程序 × 穷举注入 | 4800 程序，对拍参考解释器 | 0 不一致 |
| 只发射 7 条合法指令 | 扫描汇编输出 | 通过 |

| 公开自测 | `evaluator.py --level l3` | 通过 |

**最大的未知**：`c[k]` 的映射读法（见上文）。如果组委会实际按测量语句顺序而不是按下标注入，
乱序测量的用例会错。可以在 `codegen.py` 里改一行映射函数应对，但现在没有办法确认哪种是对的。

**次要未知**：量子操作序列的返回格式。契约只写了 `Tuple[list, str]`，公开 evaluator 只检查
`isinstance(list)`。本实现返回归一化的 QASM 语句字符串（`"cx q[0], q[1];"`），因为它既能被
解析也能被字符串比对。如果组委会期望的是结构化的 dict 或元组，格式会对不上——这点没法从
现有文档确认。

**Bonus 未做**：自定义量子 RISC-V 扩展指令（+8 分）需要指令编码规格、fork 官方模拟器加指令、
端到端测试三件套齐全，本次没有实现。
